# Local Media Blobs retained after cloud confirm

New and downloaded audio is stored as a **Local Media Blob** on the device. When the cloud confirms the **Audio File**, the blob is marked **Cloud-backed** and **kept** — we do not delete local bytes after a successful upload. That rejects the pure upload-queue pattern (delete local copy once the cloud write succeeds) sketched in early web media-persist notes, and matches desktop behavior where recorded and downloaded files normally remain under the local media folder.

Status on the blob distinguishes **Upload Pending** from **Cloud-backed**. On web, **Upload Pending** is tracked on the Local Media Blob store itself (source of truth), not a second full pending-metadata store. Normal Orbit remove of an Audio File leaves the Local Media Blob (desktop parity); hard-delete / guided-phrase-style eviction removes it. User free-space and project-switch rules for Cloud-backed copies are in ADR 0017.

On web the blobs live in a dedicated IndexedDB database (`localMedia`, see `web/src/utils/localMediaBlobStore.ts`), separate from Orbit's `transcriber` database so record migrations and media eviction stay independent. A write counts as saved only after its transaction fires `complete`; any write that creates or ends **Upload Pending** requests `durability: 'strict'` — saving one because the device copy may be the only copy, marking it **Cloud-backed** because a rolled-back flip would cause a duplicate upload — while writes that only touch Cloud-backed copies or bookkeeping use `relaxed`, since losing them costs a re-download, never audio. A blob is keyed by its client temp id until the mediafile id is known, then re-keyed, keeping the temp id for lookups; once set, the mediafile id is permanent — later writes may confirm it but are rejected if they would change it.
